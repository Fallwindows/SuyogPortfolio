Software Engineer

Persona · with Zach Yadegari

Built the systems that let a proactive AI assistant decide what deserves attention and run requests that play out over time.

The problem I solved, with an interactive visual

Persona is an iPhone assistant meant to act before you ask. It connects to Gmail, Calendar and Drive, keeps a model of who you are, and steps in when something matters. I built two of the systems behind that: the one that decides what deserves attention, and the one that runs requests that play out over time.

The problem

An assistant that watches your inbox can fail in two easy ways. It can surface everything and become one more source of notifications, or it can surface too little and be useless. The text of a message alone doesn't tell you which: "are you free later?" is worth acting on from a friend and is noise from a store.

Importance system

Everything that reaches Persona without the user asking, like an incoming email, goes through a triage step. It gathers the context that matters for that event: what Persona knows about the user, their history with the sender, and their recent conversations. Then it makes one of three decisions. It can ignore the event, notify the user, or start a deep task, a background agent run that does the work, such as checking the calendar and drafting a reply.

Every decision is stored with its reasons, and an admin view shows each event, the context that went in, and why it was ignored or acted on. In testing, a car dealership's promotion was ignored. A friend asking to hang out on the day of a family birthday became a drafted reply that offered times around the birthday errand.

Polling system

Some requests are about time rather than a single answer: "watch BTC-USD every minute for three minutes," or "call me five minutes before every meeting." I built the piece that turns a plain-English request like that into a scheduled background job, with an interval, a stop condition and a data check on every tick. The job keeps running after the user leaves the app. When the window closes, it combines the samples into one answer, such as the average price over those three minutes, and posts it back into the chat instead of pinging on every check.

Why it was interesting

The hard part wasn't calling a model. It was judgment and time. Triage runs on every email, so it has to be cheap, but it also needs enough context to get the call right. It also has to explain itself, because when software acts on your behalf, you need to see why. Polling meant moving work off the phone into jobs that outlive the conversation and finish on their own.

Software Engineer

Pren · accounting startup, since shut down

Redesigned how agent-written code read from the database, so the app pulled only what changed instead of everything, every time.

The problem I solved, with an interactive visual

Pren built accounting software, and the team wanted Claude to do much of the building. My biggest fix was to how that agent-written code talked to the database.

The problem

One of the rules the agent followed was "reuse existing functions," a sensible rule for keeping a codebase small. When the first version of the app was built, the agent wrote a function that pulled everything from the database. As features were added, it did what the rule said and reused that function, so every single time the app ran, it pulled the whole database again, even when nothing had changed. No single run looked wrong, but together they sent database egress, the data read out of the database, far past our limit.

The fix

I designed a sync that only pulls new information:

  1. The app first fetches a single number: the database's version.
  2. If it matches the version the app already has, nothing else is fetched.
  3. If it's higher, the app checks the version of each individual data store.
  4. For the stores that changed, it runs the same check again and pulls only what it needs.

Why it was interesting

The bug didn't live in any one line. It came from a good rule meeting an expensive building block, and the agent kept multiplying the cost because it was being consistent. When code is written by an agent that follows rules, the functions it reaches for first need to be cheap, because they will be reused everywhere.

Independent Contractor

Acoustic metamaterial startup

Built optimization software that designs manufacturable material shapes to block or redirect sound.

What I built, with an interactive visual

Sound is a pressure wave, and a material's internal geometry decides what happens to that wave: it can trap it, cancel it, or steer it somewhere else. My software generates material shapes that manipulate those waves to block sound. Each shape is generated for a specific manufacturing method, so the designs it produces can actually be made.

Blocking isn't the only option. Redirecting the sound can be more effective than simply stopping it, and the software explores those designs too.

Why it matters

Quieter homes are the obvious use. The sharper one is defense, where drones and other equipment need to go unheard. In both, the physics and the manufacturing pull against each other. The best shape on paper is worthless if it can't be built, so the manufacturing method shapes the search from the start.
